# 验证记录

## 验证原则

验证分两层：

1. **离线自动化测试**：通过 mock 构造模型响应，稳定覆盖消息配对、异常回灌和终止分支，不消耗 API。
2. **人工模型用例**：观察真实模型能否自主组织多步调用；结果用于演示，不作为确定性准确率指标。

## 自动化测试范围

| 模块 | 覆盖点 |
|---|---|
| `context.py` | system 保留、回合完整、消息顺序、超过条数预算的边界 |
| `tools_core.py` | 正常分发、未知工具、非法参数、非法表达式、文件与目录错误；`sql_query` 的只读拦截、多语句、行数截断、空结果、表名错误，以及「工具说明里的列 = 真表的列」 |
| `react_loop.py` | 正常结束、输出截断、工具异常回灌、最大轮数兜底 |
| `graph_agent.py` | 条件边、消息 reducer、图执行上限 |
| `mcp_agent.py` | MCP schema 转换、正常结果、`is_error` 与调用异常回灌 |
| `team_agent.py` | 角色解析（含加粗/编号/中文别名/DONE/乱写）、越界工具拦截、只传本角色工具、worker 步数用尽交回原始材料、上限强制收口、账本隔离 |

运行：

```bash
pip install -r requirements-dev.txt
ruff check .
pytest
```

测试不读取 `.env`，也不会请求 DeepSeek。

2026-11-02 本地结果：**75 项测试通过**，Ruff 静态检查与格式检查通过。另行运行 `python mcp_client.py`，本地 MCP Server 成功返回 6 个工具（含运行时新增的 `sql_query`），正常调用与预期错误路径均符合协议。

## 人工用例

以下用例在 2026-10-26 的 Python 3.12 环境中进行过手工验证。模型输出会随模型版本和服务端行为变化，复验时应关注调用路径而非逐字答案。

| 用例 | 输入 | 观察点 |
|---|---|---|
| 多步任务 | 查一下西安天气，然后算一下 `25*4+10` | 工具结果回灌后，模型汇总天气与计算结果 |
| 错误恢复 | 读取 `not_exist.txt` | 文件错误作为 tool 消息回灌，Agent 不崩溃 |
| 单步任务 | 现在几点了？ | 调用时间工具后结束，不进入无意义的额外循环 |
| 轮数上限 | 设置 `max_steps=1`，提出需要多步的问题 | 补跑未执行的工具后降级作答，不再抛 `GraphRecursionError` |
| 多智能体分工 | 查一下北京的天气，再把温度和 10 相加 | 三单：researcher 只报「多云 18℃」，calculator 用工具算出 28，writer 整合 |
| 多智能体上限 | `max_rounds=1`，要求分别查两个城市并换算 | 第二轮不再请求模型，直接转 writer 用已有账本收口，答案不为空 |
| 查数据库 | 哪个品类卖得最好？销售额是多少 | 模型自己写出 `JOIN products` + `GROUP BY`，还主动加了 `WHERE status='paid'`，并在答案里说明「只统计已付款」。实测一次工具调用即完成 |

## 已验证的关键边界

### 按条数裁剪会破坏消息配对

固定条数裁剪可能留下 tool 消息，却删掉它对应的 `assistant(tool_calls)`。按回合裁剪后，同一组消息不会被拆开；自动化测试覆盖该不变量。

### LangGraph 的额度不是业务轮数

一轮 `agent → tools` 消耗两个 superstep。若把 `recursion_limit` 错写为 `max_steps + 1`，简单用例仍可能通过，但多轮任务会提前触发上限。

因此业务上限改由状态里的 `steps` 承担；`recursion_limit` 只做框架层兜底，换算公式加 5 步余量。

### 轮次掐断时，工具还没执行

`max_steps=1` 时，模型刚发完工具请求就被路由送去收尾。此时消息流末尾是一条没有配对的 `assistant(tool_calls)`：

- 直接拿去请求，OpenAI 兼容接口返回 400（每个 `tool_call` 都必须有对应的 `tool` 消息）；
- 而且手里一条材料都没有，收尾只能说「已达上限」。

修法是收尾前先补跑这些工具（工具执行不消耗模型轮次），再清理任何仍未配对的调用。实测用例从「已终止图执行」变成「18 + 10 = 28」。

### stdio 不能被日志污染

MCP stdio 模式中，stdout 是 JSON-RPC 通道。Server 日志必须写入 stderr，否则客户端可能无法解析协议消息。

### MCP 工具可以独立扩展

本地 Server 从四个工具增加到五个工具时，Agent 通过 `list_tools()` 自动发现 `list_dir`，无需修改 Agent 循环或手写 schema。

后来加 `sql_query` 又验证了一次，而且这次是**隔着协议**：`mcp_server.py` 里只多了一个 `@mcp.tool()`，`mcp_agent.py` 一行没改，`list_tools()` 就多出一个带完整表结构说明的工具，模型直接能用。
同一份工具在另外三条链路里要分别改 schema（手写版）、改角色白名单（多智能体）——**这就是「工具与 Agent 解耦」在代码量上的差别**。

接入官方 filesystem Server 后，同一个 Agent 可以获得目录列表等额外能力。这个对照说明的是**工具边界变化**，不是模型能力突然提升。

### 只读不是靠关键词黑名单

`sql_query` 不做「看到 DELETE 就拒绝」这种字符串匹配——改个大小写、塞个注释、写成 `WITH ... DELETE` 都能绕过去。真正的保证来自 SQLite 自己，三层：

1. **连接级只读**：`file:...?mode=ro`，写操作由引擎直接拒绝；
2. **authorizer**：只放行 `SELECT` / `READ` / `FUNCTION`（外加 `RECURSIVE` 支持 CTE），`PRAGMA`、`ATTACH`、`CREATE` 这类不写数据但能改会话状态的操作也一并挡掉；
3. **结果集截断**：`fetchmany(51)`，一条 `SELECT *` 不会把上下文塞满。

这里没有用户可传的 SQL 参数，所以谈不上参数化；防的是「模型写错或写野」，不是「外部注入」。错误统一转成 `ValueError` 回灌，模型能拿到 `no such table: xxx` 自己改。

### 编排的失效不是「派错人」，是「派对了人，他顺手把别人的活干了」

第一次跑多智能体用例时，分工看起来正常，但 calculator 一次都没被派到：

```text
[supervisor] 第 1 单 → researcher：查北京今天的天气和当前温度
[researcher] 结论：北京今天多云，当前气温 18℃，加上 10 等于 28。
[supervisor] 第 2 单 → writer：……18加10等于28……
```

研究员在结论里把加法做完了，Supervisor 看到账本已有答案就不再派计算员。工具白名单完全没起作用——**它挡的是「调用别人的工具」，挡不住「用自然语言自己算」**。

修法不是加调度规则，而是改角色提示：研究员「只报工具返回的原始数值，不做任何算术、换算或推断」，Supervisor 补一条「账本里有数字但没有结果时派 calculator」。改完是三单：

```text
[supervisor] → researcher：查北京今天的天气和当前温度
[researcher] 结论：北京当前天气为多云，温度是 18℃，查询时间为 ……
[supervisor] → calculator：把 18 和 10 相加，给出结果
[calculator] → calculate({'expr': '18+10'}) → 28
[supervisor] → writer：整合
```

结论：**角色边界是提示词 + 工具白名单两件事，缺一不可。** 只做白名单，等于只管住了「手」，没管住「嘴」。

## 尚未覆盖

- 长时间运行的 token 成本与延迟统计。
- 并发工具调用、网络重试和远程 MCP 部署。
- 大样本生成质量评估。
- 文件工具的权限控制与恶意输入安全测试。
- `sql_query` 只做了只读和行数上限，没有行级权限、审计日志和慢查询超时。
- 多智能体只做了 supervisor 单层调度，没有并行分支、层级嵌套和多轮协商。
